# 사용자 흐름

## 시작과 로그인

1. `/` 랜딩에서 한스푼의 메뉴 번역·식단 확인·직원 소통 가치를 확인한다.
2. “한스푼 시작하기”를 눌러 `/login`으로 이동한다.
3. Google 계정으로만 로그인한다. 이메일·비밀번호 회원가입과 다른 소셜 로그인은 제공하지 않는다.
4. 기존 프로필이 있으면 홈으로, 없으면 온보딩으로 이동한다.

랜딩과 로그인에서 언어를 바꿀 수 있고 선택은 두 화면과 이후 앱에 이어진다. Google ID Token을 받아 기존 `/api/v1/auth/google` 계약으로 전달하는 인증 흐름은 유지한다.

## 식당을 찾는 중

1. 홈에서 5개의 식당 소개/문화 콘텐츠 캐러셀을 본다. 캐러셀은 5초마다 자동 이동하며 모션 감소 설정에서는 자동 이동하지 않는다.
2. 홈에서 청담·부산·강남/역삼 등 18개 지역 칩을 선택하고, 해당 지역 중심 주변의 실제 가게를 지도에서 확인한다. 처음 진입하면 첫 버튼인 청담이 선택되며 일반/데모 홈 모두 동일하다.
3. 홈의 지도 핀으로 가게를 바꾸고, 선택 가게 카드나 전체 지도 버튼에서 같은 검색 중심을 유지한 채 풀스크린 `/map`으로 이동한다.
4. 풀스크린 지도 핀을 누르면 식당 상세 바텀시트가 올라온다.
5. 상세에서 입점/전체 레시피 인증 여부, 같은 프로필의 후기, 찜을 확인한다. 입점 식당은 ‘내 프로필로 메뉴 보기’, 그 외에는 ‘이 식당 메뉴 스캔’으로 이어진다.
6. 홈 하단 ‘한 끼가 여행이 되는 곳’에서 선택한 동네의 실제 식당 후보를 사진 카드로 둘러본다. 최대 6곳의 상호·업종·주소를 보여주며 클릭하면 해당 식당이 선택된 지도로 이동한다. 개인화/안전 순위가 아니며 현재 사진은 표시된 메뉴·공간 참고 이미지다. 상세 정책은 `restaurant-recommendations.md`를 따른다.

홈은 지역 칩에 대응하는 중심 좌표를 `POST /api/v1/stores/candidates`에 보내 반경 1km의 실제 가게를 최대 20곳 조회하며 위치 권한을 요구하지 않는다. 홈에서 `/map`으로 이동하면 전달받은 지역 중심 좌표로 즉시 시작하고, 하단 지도 탭에서 직접 `/map`에 진입한 경우에만 브라우저 현재 위치를 먼저 조회한다. 지도를 옮기면 `dragend` 시점의 중심 좌표로 후보를 다시 조회한다. 후보 응답으로 지도 위치를 다시 맞추지 않아 요청이 반복되는 것을 막고, ‘내 위치’ 버튼은 현재 위치가 아직 없으면 그 시점에 위치 권한을 요청한다. 위치 요청이 실패해도 이미 보고 있던 지역 지도는 유지하며, 직접 진입의 위치 거부·오류·8초 시간 초과 시에는 안내한다. 좌표는 후보 조회에만 사용하고 브라우저 저장소나 스캔 기록에는 저장하지 않는다.

## 입점 식당의 촬영 없는 메뉴 확인

홈/지도/촬영 화면의 식당 선택에서 입점 파트너를 고르면 `/restaurants/:id/menu`로 이동한다. 가상 전체 레시피 6종과 현재 프로필을 비교해 기존 결과 카드로 보여준다. 확인된 회피 재료 충돌은 위험, 프로필 없음·종교 인증 확인 필요는 주의로 표시한다. 확률을 임의로 만들지 않는다. 이 동선은 실제 스캔 API를 호출하지 않는다.

하단은 ‘프로필 수정하기 / 기록하기’. 식당이 연결된 상태로 기존 저장 흐름을 재사용한다. 일반 식당은 촬영 흐름을 유지한다. 기록 자체 페이지는 삭제하지 않고 마이페이지에서 계속 접근한다.

## 스캔 전

홈의 스캔 CTA는 식당 선택 시트를 한 번 제시한다. 주변/지역 후보를 누르거나 한글·영문 이름으로 검색한다. “식당 없이 계속하기”로 즉시 넘어갈 수 있다. 하단 촬영 탭에서는 `/scan`으로 직접 들어가고 화면 위 선택 행에서 식당을 연결할 수 있다.

카메라 열기/사진 선택 → 미리보기 → 분석 시작. 실서비스 모드의 카메라 권한 거부, 파일 형식/10MB 제한, 업로드 재시도 처리는 기존 동작을 유지한다.

운영 모드에서는 지원 이미지를 업로드하고 `POST /api/v1/scans`로 분석을 시작한다. 분석 화면에서 스캔 상세를 폴링해 완료·재촬영 필요·실패를 구분하고, 취소 시 진행 중인 스캔을 삭제한다. 개발 프리뷰와 명시적 데모 모드에서만 분식 13개·비건/새우 고정 결과를 사용한다.

마이페이지의 지도 언어 선택은 ‘설정’ 탭에 있다. 앱 언어와 독립적으로 기기에 저장하며 식단 프로필이 없어도 변경할 수 있다.

## 결과

요약과 적용 프로필 → 상태별 개수/필터 → 메뉴명·가격·저장한 메뉴 → 주의 재료 확률 → 이유 → 직원 확인·주문 카드 → 펼쳐 보는 근거. 큐레이션은 메뉴 목록 끝에서만 제공한다. 운영 결과의 메뉴 저장은 `scanMenuId`를 사용하고, 직원 답변은 서버에 저장한 뒤 결과를 다시 조회한다.

확률은 재료의 포함 가능성이다. 식사의 안전 확률이나 알레르기 반응 확률이 아니다. 직원 답변은 명세에 따라 서버에서 판정을 갱신하며, 프런트는 서버 결과를 다시 읽는다.

## 저장

하단의 같은 크기 버튼: “다시 스캔하기” / “기록하기”. 운영 모드에서 기록하기는 `PUT /scans/{scanId}/record`를 호출한다. 스캔 때 식당을 고른 경우 연결이 잠기고, 식당 없이 스캔했다면 기록에서 식당을 연결하거나 해제할 수 있다. 기록에 식당이 있으면 식사 후기를 작성할 수 있다.

- 식당 있음: 서버 기록의 `store`와 저장 시각을 조회한다. 스캔 때 선택한 식당은 변경할 수 없다.
- 식당 없음: 일반 스캔으로 저장한다. 나중에 식당을 연결할 수 있으며 판정은 바뀌지 않는다.
- 반복 저장은 같은 스캔 기록을 갱신한다. 선택형 식단 답변은 기록 API가 아닌 식사 후기 API로 보낸다.
- 기록 상세를 다시 열면 당시의 식단 스냅샷과 메뉴를 사용한다. 원본 사진은 보관 기한이 지나면 410 안내를 표시한다.
- 기록 이름 수정/삭제는 서버 스캔 API로 처리한다. 개발 데모의 방문 메타데이터는 `src/app/demo/`에만 저장한다.

## 미래 방문 확인

지역 후보 선택은 장소 연결이며 방문 인증은 아니다. 동의 기반 위치 후보와 현장 QR의 조합을 후속 구현한다. QR은 식당 ID를 채우는 것과 서버에서 방문을 검증하는 것을 별개로 설계한다.

## 2026-11-23 회의 피드백 반영

- 랜딩에 한식 메뉴 안내를 명시하고, 식단 버튼을 ‘직원에게 내 식단 보여주기’, 찜 목록을 ‘저장한 음식’으로 표기한다.
- 결과 재료는 API status에 따라 포함 확인·미포함 확인·포함 여부 확인 필요로 표시한다. 판정 위험도만으로 재료 포함을 확정하지 않는다.
- 결과의 주문 카드 안에서 주문·재료 제외·덜 맵게 요청을 고른다. 제외가 어렵다는 답에는 대체 음식 추천 요청 문장을 보여준다.
- 카드 화면의 자주 쓰는 문장에 현재 프로필의 알레르기를 반영한 질문을 추가한다.
- 신규 문구는 한국어·영어·아랍어 제공, 나머지 4개 언어는 기존 fallback을 유지한다.
- API V2에는 전체 데이터 규모·검증 정확도·직원 답변 반영률이 없고 별도 집계 자료도 없다. 사용자 결정에 따라 숫자를 표시하지 않고, 랜딩에서 식단 기준의 메뉴 확인·재료 포함 여부 구분·직원 질문 기능으로 제공 범위를 설명한다.

### API 응답 보완

결과 상세는 근거 구분·정보 충족 상태·서버 주의 문구·추정 기준·근거 충분도·크기별 가격을 표시한다. 근거 충분도는 포함 확률과 구별한다. 기록은 추가 조회와 실패 재시도를 제공한다. 환율 조회에 실패하면 고정 참고 환율임을 안내한다. 큐레이션 끝에서는 사용자가 검색어로 식당 후보를 조회하고 지도에 진입한다. 신규 설명은 한국어·영어·아랍어 및 기존 4개 언어 fallback을 유지한다.
